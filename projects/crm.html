01Задача

Строительной компании нужен простой учёт работ: по каждому объекту — список задач, у каждой задачи — ответственный, статус и история. Две роли:

РольВозможности
Постановщиксоздаёт, редактирует и удаляет объекты и задачи; назначает исполнителя; принимает работу или возвращает на доработку с обязательным комментарием; видит всё
Исполнительвидит только свои задачи и объекты, где они есть; берёт задачу в работу и отправляет на проверку

Главное требование заказчика — безопасность: исполнитель не должен ни увидеть, ни изменить чужое, а историю статусов нельзя подделать даже через API.

02Жизненный цикл задачи

Разрешено ровно пять переходов. Все остальные запрещены на уровне базы, а не только спрятаны в интерфейсе.

переход назначенного исполнителяпереход постановщика

Правила переходов хранятся не в коде, а в таблице task_transitions. Её читает интерфейс, чтобы показать только доступные кнопки, но решение о допуске всегда принимает база.

03Правила живут в базе

Интерфейс прячет лишние кнопки для удобства, но это не защита: любой может отправить запрос к Supabase напрямую из curl, Postman или консоли браузера. Поэтому каждый запрос проходит через несколько независимых «замков» внутри PostgreSQL:

Интерфейс

Показывает только доступные действия. Удобство, а не защита — его легко обойти.

1
Права API (GRANT)

У гостя нет прав ни на одну таблицу. Вошедший пользователь пишет только в разрешённые колонки: в tasks — название, описание, объект и исполнителя, но не статус и не автора.

2
RLS — политики строк

Включены на всех пяти таблицах. Исполнитель физически получает из базы только свои задачи; чужая задача по прямому адресу — «не найдена».

3
Функция change_task_status()

Единственный способ сменить статус. Проверяет, кто вызывает, назначен ли он, разрешён ли переход и есть ли обязательный комментарий.

4
Триггеры

Страж не даёт изменить статус в обход функции. Журнал статусов только дописывается: изменить или удалить запись нельзя даже владельцу базы.

Служебные функции лежат в схеме private, которую Supabase не публикует наружу. Роль пользователя берётся из app_metadata, которую пишет только администратор, — а не из user_metadata, которую пользователь может править сам.

05Единственная «дверь» для статуса

Сокращённая версия функции из миграции — по шагам видно, что проверяется:

create function public.change_task_status(p_task_id uuid, p_new_status public.task_status, p_comment text default null)
returns public.tasks
language plpgsql security definer set search_path = ''
as $$
begin
  -- 1. Кто вызывает: без входа — отказ
  -- 2. Блокируем строку задачи (for update): два одновременных нажатия не обгонят друг друга.
  --    Чужая задача для исполнителя выглядит так же, как несуществующая:
  if not found or (v_role = 'executor' and v_task.executor_id <> v_uid) then
    raise exception 'Задача не найдена' using errcode = 'P0002';
  end if;
  -- 3. Есть ли такой переход в таблице task_transitions — иначе «Переход запрещён»
  -- 4. Имеет ли право именно этот пользователь (постановщик / назначенный исполнитель)
  -- 5. Комментарий из одних пробелов и переводов строк считается пустым
  -- 6. Меняем статус и пишем журнал в одной транзакции
end;
$$;

А так выглядит попытка обойти функцию с токеном исполнителя:

# Поменять статус напрямую, минуя функцию
curl -X PATCH "$URL/rest/v1/tasks?id=eq.<id своей задачи>" \
  -H "apikey: $KEY" -H "Authorization: Bearer $TOKEN" \
  -d '{"status": "accepted"}'
# → permission denied: права на запись в колонку status нет

# Запрещённый переход через функцию: из «Новая» сразу «На проверке»
curl -X POST "$URL/rest/v1/rpc/change_task_status" ... -d '{"p_new_status": "in_review", ...}'
# → Переход из «Новая» в «На проверке» запрещён

06Как это проверено

  • 99 автотестов правил базы (npm run test:db). Миграции применяются к PostgreSQL прямо в памяти (PGlite), без Docker и облака, а запросы выполняются под ролями Supabase — так же, как их выполняет API.
  • Полная матрица переходов: для всех 25 пар «из какого статуса → в какой» проверены свой исполнитель, чужой исполнитель и постановщик — разрешено ровно то, что в ТЗ.
  • 31 проверка на живом проекте (npm run test:live): обычные HTTP-запросы с публичным ключом, как у любого постороннего клиента. Данные не меняются. Результат — 31 из 31.
  • Поиск секретов (npm run check:secrets) — в репозитории, сборке и всей истории git. Приложение вообще откажется запускаться, если в него по ошибке подставить секретный ключ.
  • Штатные проверки Supabase — одно осознанное предупреждение: функция смены статуса выполняется с правами владельца, потому что она и есть единственная «дверь» и сама проверяет, кто вызывает.

Тест нашёл и настоящую ошибку: стандартная обрезка пробелов в PostgreSQL не убирает переводы строк, и «комментарий» из одних Enter проходил проверку. Теперь такой комментарий считается пустым.

07Решения и компромиссы

  • Принять задачу может любой постановщик, а не только автор: в ТЗ указана роль. Ограничение «только автор» — одна строка в функции.
  • Журнал переживает удаление задачи. У журнала нет внешнего ключа на задачу, поэтому удаление задачи не стирает историю, а исполнителю она становится недоступна.
  • Имя в журнале хранится снимком на момент действия: переименование или удаление пользователя историю не портит.
  • Новый пользователь — исполнитель (минимум прав), постановщиком его делает только администратор. Регистрация закрыта.
  • Строка задачи блокируется при смене статуса: два одновременных нажатия не приведут к гонке.

08Стек и структура

  • Фронтенд: React 19, TypeScript 5.9, Vite, Mantine 8, TanStack Query. При выходе и смене пользователя кэш очищается, чтобы данные одного человека не попали к другому.
  • Бэкенд: Supabase — PostgreSQL, Auth, REST API. Четыре миграции: схема, профили и помощники, права доступа, жизненный цикл задачи.
  • Тесты: Node test runner, PGlite, проверки живого API.
  • Деплой: Vercel; в браузер уходит только публичный ключ.
